### 2. Will the reconciliation job schedule alongside ingestion?

**What it needs:** Checking whether the node's allocatable memory covers all the memory requests together.

**No, it won't schedule.** The job will stay `Pending` unless you add capacity or reduce requests.

| Item | Memory |
|---|---|
| Node total | 8.0 GiB |
| Reserved (kubelet + system) | −1.5 GiB |
| **Allocatable** | **6.5 GiB** |
| Ingestion (3 × 2 GiB requests) | −6.0 GiB |
| **Remaining** | **0.5 GiB** |
| Reconciliation job request | 2.0 GiB, which is **1.5 GiB short** |

In practice the gap is wider. DaemonSets such as kube-proxy, the CNI agent, and log shippers usually have memory requests that also count against the 6.5 GiB.

Ways to fix it:
- Add a node or move to a bigger one.
- Lower the job's request if it really needs less than 2 GiB.
- Lower ingestion's requests.
- Scale ingestion down while the job runs.

Note that the 3rd ingestion replica alone fits, using 6 of 6.5 GiB, so the bump itself won't fail. Only the job will.

### 3. Liveness vs readiness probe explanation

**What it needs:** A short, accurate explanation you can forward.

> A **readiness probe** tells Kubernetes whether a pod is ready to receive traffic. If it fails, the pod is taken out of the Service's endpoints but keeps running, which is useful during startup or when a dependency is temporarily down. A **liveness probe** tells Kubernetes whether the container is still healthy. If it fails, the kubelet restarts the container, so use it only for states the app can't recover from on its own, like a deadlock. In short, readiness failing means "stop sending me traffic" and liveness failing means "restart me."
