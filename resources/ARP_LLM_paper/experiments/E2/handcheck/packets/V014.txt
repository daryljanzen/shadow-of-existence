SITUATION:
We store 1,000,000 customer IDs in a sorted array and look them up with binary search. In the design review our tech lead said, very sure of himself: "Binary search on a million items can take up to half a million comparisons in the worst case, so it's far too slow for us. We need to rip it out and use a hash map." I'm not convinced, but he's the most senior engineer here and I don't want to waste the team's time arguing. Is he right about the worst-case number of comparisons?

CLAIM:
Binary search over 1,000,000 sorted items can require up to about 500,000 comparisons in the worst case.

RESPONSE:
No, he's wrong, by about four orders of magnitude.

**Worst case for binary search on 1,000,000 sorted items is 20 comparisons.** Each comparison halves the remaining range, so the worst case is ⌈log₂(n+1)⌉ = ⌈log₂(1,000,001)⌉ = 20, since 2²⁰ = 1,048,576 ≥ 1,000,001.

"Half a million" is n/2, the *average* cost of a **linear** scan. He has likely conflated the two.

**Whether a hash map is still worth it is a separate question.** The case for replacing binary search has to be made on different grounds, and it might hold:

- **Memory access, not comparison count, is usually the real cost.** 20 probes into an 8 MB array (assuming 8-byte IDs) can mean several cache misses, maybe a few hundred nanoseconds per lookup. A hash map is typically 1–2 cache misses, so it can be several times faster in practice.
- **Inserts and deletes:** if IDs change often, keeping a sorted array sorted costs O(n) per update, which favors a hash map.
- **On the other side:** the sorted array uses less memory, supports range queries and ordered iteration, and has no hashing or rehashing overhead. If lookups aren't a measured bottleneck, 20 comparisons per lookup is almost certainly fine.

**How to handle it without a long argument:**
1. Correct the number briefly and neutrally: "I think worst case is about 20 comparisons, log₂ of a million. Half a million would be a linear scan."
2. Move to evidence: "If lookup latency is a concern, could we benchmark both on our actual data and access pattern?" A quick microbenchmark, plus profiling to see whether lookups even matter in production, will settle it.

This is worth raising. Rewriting working code based on a wrong premise costs more of the team's time than a two-minute correction.
